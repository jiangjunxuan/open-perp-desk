# 订单恢复与交易所状态

## 发单中断

发单前先在 SQLite 提交 `preparing` 占位，网络发单前切换为 `submitting`。
超时或协程中断会记录 `submission_unknown`；进程直接退出时可能保留前两个状态。
这些状态均继续占用风险额度，不按时间自动删除，不因一次“查无订单”释放。

REST 对账会对未被 pending/history 快照覆盖的活动普通订单执行精确查单。
有交易所编号时使用 `ordId`，否则使用原始 `clOrdId`，并验证：

- 当前账户范围与发单时保存的范围一致。
- 交易所编号、客户端编号、合约和已保存的订单身份一致。
- 本地下单意图的方向、持仓模式、保证金模式、订单类型和数量一致。
- 只有客户端编号可用时，交易所创建时间必须在本地占位前 10 秒到后 120 秒内。
- 返回可确认的交易所状态和有效更新时间。

OKX `51603`、空结果、身份不一致、超时或无有效时间均保持待确认。
恢复过程只读交易所，不重新下单。成功确认后，原幂等键仍返回原订单。

## 账户范围

新订单保存由 REST 地址、Demo 标记和 API key 派生的不可逆账户范围标识，
不保存 API secret 或 passphrase。活动订单范围与当前配置冲突时拒绝新发单。

旧版本本地订单若没有范围证据，不会自动归属到当前账户。必须先核对原账户
与交易所订单记录；目前没有自动释放或自动重新绑定入口。不能通过清空订单表
来“解决”此状态，否则会丢失幂等证据。

## 单调更新

普通订单和算法订单使用不同的 `order_kind`。交易所更新时间单独存为
`exchange_updated_ms`，不拿本地 HTTP 响应到达时间代替交易所事件时间。
REST 和 WebSocket 写入在同一个 SQLite 事务中检查身份与状态：

- 旧更新时间不能覆盖新回报。
- 终态不能被活动状态重新打开。
- 部分成交不能被后到的挂单快照降级。
- 相同快照不重复修改风险预算版本。
- 本地下单时的数量、风险预留、保护价和策略来源不被回报清空。

收到撤单 API 的成功受理只记录 `canceling`。最终撤销或成交状态继续由交易所
快照确认。止盈止损撤单走算法订单接口，不把算法编号当成普通 `ordId`。

## 原生保护单

止盈止损 pending 查询带 `ordType=conditional,oco`，历史查询分别读取
`effective`、`canceled`、`order_failed`，使用 `algoId` 游标完整分页。
`actualSide` 是触发分支，不用作买卖方向；待触发数量优先读取 `sz`，
不能让字符串 `"0"` 的 `actualSz` 覆盖真实委托数量。

只有 `reduceOnly` 或明确的双向持仓平仓方向才可判定为减仓单。
发单预检另外扫描公开文档列出的活动算法类别；存在可能开仓但尚不能可靠估值
的算法委托时拒绝新订单，不把所有算法单一概排除在风险预算之外。
浮动盈亏缺失时同样拒绝发单，不将未知亏损显示或计算为零。

## 对账结果

接口部分失败会写入 `errors`，对账器保留上一次成功时间并显示当前错误。
`last_attempt_at` 表示尝试时间，`last_sync_at` 只表示最近一次完整成功对账。
自动 Worker 继续在不完整账户快照下停止本轮交易。

## 验证边界

`infra/demo-smoke.py` 使用真实 API 子进程、临时 SQLite 和本机交易所协议服务，
从 HTTP 分析入口走到订单、成交、原生保护、Worker 和通知。
其中崩溃测试在本机交易所接收订单、API 尚未收到响应时强制终止进程，
并隐藏常规订单历史，要求重启后的精确 `clOrdId` 查询恢复订单，而不能重发。

账户同步先应用当前快照的普通订单和精确恢复结果，再从已确认的成交订单
回填持仓止盈止损。这样，单次 REST 同步或私有流部分成交不会遗漏保护价。
本地保护价来源仍是本地订单元数据，不等同于证明交易所原生保护已生效；
原生保护状态由独立算法单对账确认。

`test_order_recovery.py` 覆盖签名请求参数、分页、查无订单、账户错配、
乱序快照、SQLite 重新打开和发单途中子进程退出。进程演练使用本地模拟交易端，
验证退出后持久化占位仍在，查单恢复后同一信号只留下一个发送记录。

这些测试不是 OKX Demo 实际成交验收。真实私有 WebSocket、保护单触发、
网络分区、服务器断电、PushPlus 到达及部署回滚仍需要目标环境验证。
