# 订单恢复与交易所状态

## 发单中断

发单前先在 SQLite 提交 `preparing` 占位，网络发单前切换为 `submitting`。
超时或协程中断会记录 `submission_unknown`；进程直接退出时可能保留前两个状态。
这些状态均继续占用风险额度，不按时间自动删除，不因一次“查无订单”释放。

REST 对账会对未被 pending/history 快照覆盖的活动普通订单执行精确查单。
有交易所编号时使用 `ordId`，否则使用原始 `clOrdId`，并验证：

- 当前账户范围与发单时保存的范围一致。
- 交易所编号、客户端编号、合约和已保存的订单身份一致。
- 本地下单意图的方向、持仓模式、保证金模式、订单类型和数量一致。
- 只有客户端编号可用时，交易所创建时间必须在本地占位前 10 秒到后 120 秒内。
- 返回可确认的交易所状态和有效更新时间。

OKX `51603`、空结果、身份不一致、超时或无有效时间均保持待确认。
恢复过程只读交易所，不重新下单。成功确认后，原幂等键仍返回原订单。

## 账户范围

新订单保存由 REST 地址、Demo 标记和 API key 派生的不可逆账户范围标识，
不保存 API secret 或 passphrase。活动订单范围与当前配置冲突时拒绝新发单。

旧版本本地订单若没有范围证据，不会自动归属到当前账户。必须先核对原账户
与交易所订单记录；目前没有自动释放或自动重新绑定入口。不能通过清空订单表
来“解决”此状态，否则会丢失幂等证据。

## 单调更新

普通订单和算法订单使用不同的 `order_kind`。交易所更新时间单独存为
`exchange_updated_ms`，不拿本地 HTTP 响应到达时间代替交易所事件时间。
REST 和 WebSocket 写入在同一个 SQLite 事务中检查身份与状态：

- 旧更新时间不能覆盖新回报。
- 终态不能被活动状态重新打开。
- 部分成交不能被后到的挂单快照降级。
- 相同快照不重复修改风险预算版本。
- 本地下单时的数量、风险预留、保护价和策略来源不被回报清空。

收到撤单 API 的成功受理只记录 `canceling`。最终撤销或成交状态继续由交易所
快照确认。止盈止损撤单走算法订单接口，不把算法编号当成普通 `ordId`。

## 原生保护单

止盈止损 pending 查询带 `ordType=conditional,oco`，历史查询分别读取
`effective`、`canceled`、`order_failed`，使用 `algoId` 游标完整分页。
`actualSide` 是触发分支，不用作买卖方向；待触发数量优先读取 `sz`，
不能让字符串 `"0"` 的 `actualSz` 覆盖真实委托数量。
本地尚未终结的算法单没有出现在列表时，按 `algoId` 精确查询
`GET /api/v5/trade/order-algo`，并核对账户、合约及客户端编号。
查无结果、超时或身份不符只记为未解决，不当作已经撤销；对账失败会阻止 Worker 本轮交易。

只有 `reduceOnly` 或明确的双向持仓平仓方向才可判定为减仓单。
发单预检另外扫描公开文档列出的活动算法类别；存在可能开仓但尚不能可靠估值
的算法委托时拒绝新订单，不把所有算法单一概排除在风险预算之外。
浮动盈亏缺失时同样拒绝发单，不将未知亏损显示或计算为零。

## 对账结果

接口部分失败会写入 `errors`，对账器保留上一次成功时间并显示当前错误。
`last_attempt_at` 表示尝试时间，`last_sync_at` 只表示最近一次完整成功对账。
自动 Worker 继续在不完整账户快照下停止本轮交易。

## 验证边界

`infra/demo-smoke.py` 使用真实 API 子进程、临时 SQLite 和本机交易所协议服务，
从 HTTP 分析入口走到订单、成交、原生保护、Worker 和通知。
其中崩溃测试在本机交易所接收订单、API 尚未收到响应时强制终止进程，
并隐藏常规订单历史，要求重启后的精确 `clOrdId` 查询恢复订单，而不能重发。

账户同步先应用当前快照的普通订单和精确恢复结果，再依据持仓 `tradeId`
关联已确认的开仓订单。匹配要求账户范围、合约、`posSide`、保证金模式及买卖方向
全部一致，订单号与客户端编号吻合，已成交数量能够覆盖当前持仓且不超过委托数量。
只接受唯一的普通开仓成交，不能从历史列表中随意挑一张同方向订单；
匹配查询也不受最近 500 条订单的展示上限影响。

本地账本保存成交关联和保护来源订单。缺少成交编号、账户依据、有效数量或出现
多重匹配时，本地保护价为空；已经关联的持仓失去依据时记录一次告警和通知事件。
手动成交改变了当前持仓最后成交编号后，也不会继续套用无法证明关联的旧保护价。
这些处理不撤销交易所原生保护单；本地保护价为空不证明交易所没有原生保护。

账户身份或保护来源改变时会更新保护周期编号，以免复用旧来源的平仓幂等结果。
自动保护触发后，共用交易前校验再次核对交易所持仓的最后成交编号；
如果持仓在判断后已经改变，返回 `close_position_changed`，不发出该次平仓请求。
旧数据库新增字段不会凭空构造关联；须由新的有效账户快照恢复证明。

已完全成交的开仓单还须通过本系统生成的 `attachAlgoClOrdId` 对应原生
`algoClOrdId`，以原生订单当前参数作为本地兜底依据；不使用 `attachAlgoId`
冒充原生 `algoId`。没有原生证据时，不把开仓时的历史附带参数当成仍然有效。
部分成交且尚未观测到原生单时，只使用该普通订单当前快照中明确返回的附带保护参数；
附带参数被移除时不恢复本地下单意图中的旧值。

当前兜底支持固定张数、标记价格触发和市价执行的 OCO 或单边条件保护。
改价与移除单边保护会更新本地价格；撤销、暂停、已触发、失败、部分生效、
数量不符、最新成交价/指数触发、限价执行或分拆/动态保护等不支持的口径会暂停该笔本地兜底。
REST 和 WS 均先更新原生状态，再计算本地保护；仅收到算法推送、没有新持仓事件，
甚至普通私有流暂时断开时，也会刷新已经缓存的持仓保护，不重放旧持仓数量。

保护触发携带参数快照；发单预检再读取当前活动原生订单或部分成交父订单，
发现参数改变或单据消失时返回 `close_protection_changed`，缺少依据时返回
`close_protection_unverified`，均不发单。保护参数指纹纳入幂等键，
以免修改后的有效保护复用旧参数的预览/发单结果。
这是两次读取之间的保守核对，不是与交易所修改操作跨系统原子执行；
原生保护与本地平仓仍依赖减仓约束、可平数量及待确认平仓拦截。

对外部手动交易、多笔开仓合并形成的持仓，
如果当前持仓不能由该条开仓成交完整覆盖，则保留未关联状态，不猜测整仓保护价。
字段口径参考 OKX 官方文档：
`https://www.okx.com/docs-v5/en/#trading-account-rest-api-get-positions`、
`https://www.okx.com/docs-v5/en/#order-book-trading-algo-trading-get-algo-order-details`。

`test_order_recovery.py` 覆盖签名请求参数、分页、查无订单、账户错配、
乱序快照、SQLite 重新打开和发单途中子进程退出。进程演练使用本地模拟交易端，
验证退出后持久化占位仍在，查单恢复后同一信号只留下一个发送记录。

这些测试不是 OKX Demo 实际成交验收。真实私有 WebSocket、保护单触发、
网络分区、服务器断电、PushPlus 到达及部署回滚仍需要目标环境验证。
