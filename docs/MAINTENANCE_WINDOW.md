## 窗口前

1. 确认实例 ID、地区和公网地址一致；保持云控制台可用。
   无法证明能够从控制台重新开机时，禁止关机或强制断电。
2. 确认只做无交易的恢复演练：Demo 模式，执行/自动交易/实盘闸门关闭，
   持久急停有效，研究空闲，无订单、持仓或待处理交易任务。
   发现私有交易状态时立即停止，另行制定带交易所对账的窗口。
3. TradingView 保持只接收、Dry Run；记录所有待处理告警，禁止通过降低有效期校验、
   改写 ID 或自动重发来制造“恢复成功”。平台真实投递验收可独立提前完成。
4. 重新运行部署预检并生成在线一致性快照，把快照、配置和校验清单复制到另一台机器；
   重新验证摘要和 SQLite 完整性。归档当前容器 digest、配置摘要和宿主机 boot ID。
5. 记录同机服务与站点基线，确认其他项目负责人接受停机；
   不使用 `pm2 restart all`、全局配置覆盖或删除数据卷。
6. 从宿主机之外开始记录 HTTPS、行情/系统 SSE 连续性和 SSH 可达性，
   记录实际失联与恢复时间。不能在恢复后新建连接冒充原客户端自动恢复。

## 执行与恢复

1. 管理员在已确认的窗口内选择并记录故障类型：
   正常 `reboot` 只能算整机重启；正常关机后开机只能算有序电源循环；
   只有实际强制断电、恢复供电的独立证据才能算断电恢复。
   不为取得标签主动损坏文件系统，也不在未确认影响范围时强制断电。
2. 从云控制台观察停机和开机状态，保留实例操作记录及时间。
   不以 SSH 会话断开作为电源已关闭的唯一证据。
3. 开机后先观察 Docker 和系统服务是否自动拉起，记录新 boot ID。
   在取证前不要手动 `compose up` 或重启服务来掩盖自动启动失败。
4. 核对目标镜像、数据卷、配置摘要、数据表、原有报告/策略/标记和急停状态；
   重新验证管理员鉴权、readiness、公网资源、行情新鲜度和真实 SSE 恢复。
5. 核对 TradingView 接收记录，没有将旧告警重复执行；本次无交易演练的订单数仍应为零。
   未经再次批准不解除急停或开启交易。
6. 核对同机其他项目与窗口前基线。原先 403 或停止的服务应单独保留说明，
   不为让检查“全绿”而改变其权限或启动状态。

## 中止与回滚

- 任一身份、备份、权限或安全锁检查失败，停在当前步骤，不开始断电。
- 开机未恢复，先使用已确认的云控制台排查；不要持续强制电源循环。
- 服务自动启动失败，先留存日志和容器退出原因，再按目标项目恢复，记录人工干预。
- 仅在数据库损坏或数据不一致得到确认后评估恢复快照；恢复会回退窗口后的写入，
  须核对数据差异并明确批准，不能为了缩短维护直接覆盖现库。
- 维护完成记录必须分别说明自动恢复、人工协助、数据损失、外网中断时间和未验证项，
  不把无交易状态演练写成真实 OKX 在途订单恢复。
