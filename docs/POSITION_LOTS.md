# 合并持仓分单记录

## 当前范围

持仓明细可以展示多笔开仓的剩余张数、原始开仓张数、原生保护张数与止盈止损价格。
这是本地虚拟分单账本，不是交易所为净持仓提供的独立子仓位。
分单重建和订阅页面仍为只读。自动交易必须显式启用 Worker，并经过下面的保护接管流程；
核验成功不直接授权下单。页面的执行状态来自服务器 Worker 和执行闸门，不受浏览器暂停看盘影响。

## 重建依据

- 使用持仓的账户范围、合约、持仓方向、保证金模式及最后成交编号确定起点。
- 对 `fills-history` 按 `billId` 分页，向前回溯到能够核验的空仓边界；
  不把最近 100 条成交当作完整历史，也不使用 `posBal` 推算合约张数。
- 每条成交必须与对应普通订单身份、方向、累计成交量及成交业务类型一致。
  本地缺少订单时只读精确查单，不生成交易请求。
- 同一开仓单的多次成交归为一笔。开仓均价是该单在本次仓位生命周期内的加权成交均价。
- 本地保护平仓使用发单前保存的不可变保护上下文确定开仓归属；
  原生保护成交通过算法订单的普通子订单编号关联。
- 没有明确保护关联的手动或外部减仓采用显式的先进先出虚拟分配。
  这是本地记账策略，不代表交易所提供了分单归属。
- 有明确归属的保护平仓不得扣减其他开仓单；数量超出该单剩余张数时停止核验。

## 失效与显示

历史不足、重复成交编号、身份不匹配、未知成交业务、单次成交跨越净方向反转，
以及核验期间持仓或订单变化，均返回待核对状态，不展示部分推测的分单结果。
仓位关闭、重开、切换账户或订单代次变化会使旧快照失效。
SQLite 升级仅增加表和字段；旧保护单缺失的上下文不推测补写，也不按手动减仓处理。
核验策略版本升级会使旧分单快照失效，下一次对账重新重建。

当前受支持的原生保护是固定张数、标记价格触发的市价止盈止损。
界面区分数量匹配、数量过多或不足、已撤销、已触发、部分触发和无法核验。
“原生数量匹配”仅表示本地最新核验结果，不承诺交易所当前一定可成交。
持仓接口和私有 SSE 使用同一数据读取路径；订阅页面不会触发交易所查询或交易。
实时更新保留分单展开状态、键盘焦点和表格滚动位置。

## 原生保护接管

当前自动接管支持本程序已经完全成交的开仓单，以及与之唯一关联的固定张数、标记价触发、
市价执行的原生保护；部分成交的开仓单通过下述余单撤销流程接管。
多个开仓单合并为一个仓位时，只平掉命中条件的那一笔。

1. Worker 使用有效标记价格判断触发条件，重新执行账户快照和独立风控检查。
2. 将开仓、分单、原生保护编号、保护参数、触发原因和价格持久化，形成接管意图。
3. 精确查询原生单并核对参数后发出撤销请求。成功回执只表示受理，不表示已经撤销。
4. 精确查询证明原生单已撤销、参数仍匹配且没有派生平仓单后，进入本地接管；
   原生单已经触发时先走下述终态成交核对流程。
5. 再次对账并核对当前分单余量，使用统一执行器提交 reduce-only 平仓。
   分单快照、订单占位和接管序号在数据库事务中验证，避免并发重复占用。
6. 未确认或部分成交的普通平仓单不重发；确认部分成交后已撤销时，
   下一次对账按该分单实际剩余数量继续，使用新的执行序号。

触发意图一旦建立便会保留，价格回到阈值以内不会自动撤销平仓计划。
HTTP 超时、503 或进程退出后先查询交易所。原生撤单重试必须先重新确认同一原生单仍为 live，
并经过持久化退避，行情失效时暂停撤单重试并保留原生保护；
订单提交结果未知则只对账，不自动重复发单。
原生保护抢先触发时先核对其普通子订单；未确认的原生或本地平仓存在时不把接管标记为完成。
接管期间阻止同一账户、同一合约的新开仓，但不放宽急停、执行开关或实盘独立闸门。

持仓页同时展示接管汇总和分单状态；仓位已经归零但平仓结果未知时，汇总仍保留。
`GET /api/v1/protection/handoffs` 和私有 SSE 的 `protection_handoffs` 事件都要求管理员授权，
仅读取账本，不触发交易。已确认状态变化与平仓提交进入审计和可选 PushPlus 通知。

### 部分成交开仓

- 以交易所当前附带保护参数判断触发，不将历史附带参数显示为已生效的原生保护。
- 先持久化 `opening_cancel_pending` 意图，再精确查询开仓单、核对参数并撤销未成交余量。
  撤单回执不是终态；超时或 503 后查询同一订单，退避期结束且行情有效才再次请求撤销。
- 撤单期间增加的成交通过完整成交链归入同一分单，平仓量取终态对账后的剩余张数。
- 已撤销且累计成交量小于委托量时，只有算法精确查询明确返回 `51603`、本地没有曾存在的
  原生单证据、当前活动算法列表没有对应保护，才允许走未生成原生保护的接管路径。
  查询异常、空响应或历史查询缺失均不等同于此证据。
- 若撤单竞态中开仓已经全部成交，则进入 `native_pending` 等待原生保护生成。
  单次查不到原生单不会授权本地平仓。发现原生单后，以独立且只写一次的证据绑定原始意图，
  继续执行原生撤销确认；若原生已触发，先核对子订单，确认终态后再处理分单余量。
- 每次提交前再次查询开仓终态及保护状态；订单原子占位还会核对完整接管上下文。
  所有阶段可跨进程重启恢复，尚未确认的平仓继续等待对账。

这里依据 OKX 文档中“完全成交后生成附带算法单”的契约处理取消后的部分成交；
实际 OKX Demo 的创建延迟及撤单竞态仍须验收。附带保护创建失败、参数变更或无法核验的状态
保持拦截并要求复核，不从历史参数推测或自动放宽检查。

虚拟分单不是交易所原子子仓位。其他终端同时修改仓位可能发生在任何一次校验之后，
不能把本地分配及 reduce-only 约束当作对外部并发操作的绝对隔离。

### 原生触发后的剩余数量

- 已触发但仍有分单余量时，即使标记价格已经恢复，也会进入原生成交核对流程。
  这不是重新判断价格触发，而是完成已经发生的保护退出。
- 按 `ordIdList` 精确查询每个普通子订单，核对账户、合约、方向、保证金模式、
  市价类型和减仓约束。重复编号、派生算法单或不支持的高级类型均不授权本地平仓。
- `actualSz` 是原生单实际发出的委托张数，不是成交张数；必须与子订单委托量之和一致。
  成交量另取每个子订单的 `accFillSz`，且所有子订单必须已经成交完毕或撤销。
- 原生单为 `partially_effective` 时，先持久化“原生余单撤销待确认”状态，
  再撤销其剩余委托；收到成功回执后仍须精确查询到终态。
  暂时查询失败时保持等待，撤销响应丢失时先查单，避免盲目重复请求。
- 原生终态和子订单量以规范化十进制证据只写一次；再次查询与已保存证据不一致时转入复核。
  不以重新读取的新值悄悄替换旧证据。短暂查询故障不会自动解除或重发本地平仓。
- 重新对账后，本地平仓仅使用该分单的剩余量，不直接用原生委托量减去成交量计算。
  发单前复查原生及子订单，数据库原子占位再次核对完整证据。
  后续本地平仓发生部分成交时，仍须等其撤销终态，再按账本余量继续。
- 原生成交归属在原生单已撤销时仍保留，不退回先进先出分配；无关开仓分单不受影响。
  所有阶段可重启恢复，真实 OKX Demo 的终态数据和竞态行为仍待验收。

## 保护维护人工复核

保护接管和数量调整进入 `review` 后，持仓页会显示专用复核入口，列出原保护数量、
止盈止损、开仓单、原生单和异常原因。与“附带保护创建失败”的事故解除入口分开处理。

- “恢复原流程”重新只读对账并精确查询开仓、原生保护及必要的普通子订单。原参数、
  绑定关系或已保存的原生成交终态依据不匹配时拒绝恢复，不用新参数覆盖旧意图。
- 恢复会保留原触发意图、撤单次数、退避时间、改量请求编号、平仓序号和未确认订单。
  不因价格恢复而取消原退出计划，不因管理员复核而重发普通平仓。
- 改量目标已经落后于经核验的分单余量时，只有原请求尚未发出或原目标已确认生效，
  才在同一数据库事务中结束旧记录并建立新数量维护，避免短暂放开同合约新开仓。
  旧请求结果仍未知时维持复核，不丢弃原维护记录。
- “仓位归零后结案”要求同账户、同合约仓位已关闭且数量为零，没有活动或未知结果的普通委托，
  原生保护已确认终止，原生派生平仓和已存在的本地平仓也必须确认结束。修改过参数的保护
  只有在这个归零路径下才能结案；只看到空持仓、撤单回执或查询异常不够。
- 不存在原生单的证据只沿用已撤销且部分成交开仓的受支持路径：精确查询明确返回 `51603`，
  且没有曾存在原生保护的本地证据。全部成交后仍在等待原生单生成的记录不能据此结案。
- 复核接口不下单、不撤单、不改量，不启用 Worker，不改变急停、执行或实盘闸门。
  已启用的 Worker 只有在其他闸门放行时才继续原保护流程，并照常重新检查交易所状态。

接口为 `POST /api/v1/protection/handoffs/{id}/review` 和
`POST /api/v1/protection/adjustments/{id}/review`，要求管理员授权，
请求包含页面所见的 `expected_version`、`resolution`（`resume` 或 `position_closed`）
以及 3 至 500 字的 `note`。只接受 `review` 记录。
复核版本、账户、仓位生命周期、订单代次和分单快照在提交事务中重新核对，
状态变更、可选替代维护记录与审计一起提交；任何冲突或审计失败都会回滚。
列表和私有 SSE 提供同一版本及保护依据。新推送不会覆盖备注或抢走对话框焦点；
版本变化或请求失败后必须重新读取记录才可再次提交，迟到响应不能删除新状态。

本机协议测试覆盖恢复后的 Worker 续跑、部分成交开仓、原生子订单未结束、
数量目标变化、未知改量结果、归零结案、账户/仓位/订单变化、并发复核、急停保留与重开数据库。
浏览器测试覆盖深浅主题、电脑/手机、版本冲突、授权失效和零交易所写请求。
这些结果仍不是实际 OKX Demo 验收，也不提供与其他交易终端操作之间的跨系统原子隔离。

### 未触发保护的数量维护

- 对仍为 `live`、固定张数、标记价触发、市价执行且参数可复现的原生保护，
  Worker 会把最新已核验分单余量作为目标数量；目标与当前原生数量相同时不发请求。
- 数量调整使用 OKX `amend-algos`，只发送 `newSz`、原生算法编号、请求编号和
  `cxlOnFail=false`，不会借改量接口修改止盈止损价格。目标数量必须通过合约最小张数、
  张数步长和交易所上限检查。
- 成功回执只表示请求受理。服务会再次查原生单，只有当前数量和原有止盈止损证据都匹配
  才标记已同步；超时、503、进程退出或回执字段不完整时保留待确认状态，不盲目重发。
  对归零分单不发送非法的零数量改量，而是核验原生单仍为未触发后撤销它。
- 数量维护与保护接管使用同一账户和合约互斥范围。原生单已经触发时让位给接管流程；
  外部参数变化、触发子订单缺失、保护终态异常或账户/分单快照变化均转人工核对。
  维护记录、目标张数和最后状态经 SQLite 持久化，并通过管理员 SSE 推送到持仓页。
